# 테스트 가이드

## 왜 이 체계가 필요했나

Phase 0 이전 이 프로젝트에는 **테스트 파일이 하나도 없었다.** 그런데 CI는 테스트를
실행하고 있었고, 존재하지 않는 `jest-sonar-reporter`를 참조해 항상 실패했으며,
`continue-on-error: true`가 그 실패를 삼키고 있었다. **품질 게이트가 있는 것처럼 보이지만
아무것도 막지 않는 상태**였다.

## 3계층

| 계층         | 대상                                                   | 도구                  | 기준                  |
| ------------ | ------------------------------------------------------ | --------------------- | --------------------- |
| **유닛**     | `src/utils/`, `src/hooks/`의 순수 로직                 | Jest                  | 커버리지 **80% 강제** |
| **컴포넌트** | 상호작용 (선택지 클릭 → 점수 반영, 폼 검증, 모달 개폐) | React Testing Library | 핵심 컴포넌트 필수    |
| **스모크**   | 전 페이지가 크래시 없이 렌더 + 라우트 가드 동작        | RTL + MemoryRouter    | 전 라우트 필수        |

계층을 나누는 이유는 **실패했을 때 원인을 좁히기 위해서**다. 유닛이 깨지면 로직 문제,
스모크가 깨지면 통합 문제다.

## 파일 위치

CRA 기본 규약인 **co-located**를 따른다. 테스트를 대상 파일 바로 옆에 둔다.

```
src/utils/TimeUtil.js
src/utils/TimeUtil.test.js      ← 여기
```

`__tests__/` 디렉토리를 따로 만들지 않는다. 파일을 옮길 때 테스트가 따라오지 않는 문제가
생긴다.

## 실행

```bash
npm test          # watch 모드 (개발 중)
npm run test:ci   # CI 모드 + 커버리지 (커밋 전)
```

## 커버리지 기준

현재 `src/utils/`와 `src/hooks/`에만 80% 임계치를 건다. `package.json`의
`jest.coverageThreshold`가 단일 출처다.

**전역에 80%를 걸지 않는 이유**: 아직 테스트가 없는 컴포넌트가 수치를 0%로 끌어내려
첫날부터 CI가 빨개진다. 그러면 아무도 지키지 않게 되고, 게이트는 무시할 대상이 된다.
범위를 좁게 시작해 Phase가 진행되며 넓힌다.

## 모킹 방침

### 네트워크

**실제 네트워크 호출을 절대 하지 않는다.** axios는 모듈 단위로 모킹한다.

```js
jest.mock("../utils/axios");
```

테스트가 백엔드 상태에 의존하면 백엔드가 죽었을 때 테스트가 깨진다. 그건 테스트의 잘못이다.

### localStorage

jsdom이 제공하는 기본 구현을 그대로 쓰고, **각 테스트에서 초기화**한다.

```js
beforeEach(() => {
  localStorage.clear();
});
```

`localStorage` 직접 접근은 ESLint `no-restricted-properties`로 막혀 있지만, 테스트 파일은
`.eslintrc.json`의 `overrides`에서 예외 처리되어 있다. 저장소 상태를 직접 검증해야 하기
때문이다.

## 타임존 의존 테스트 주의

**날짜 관련 테스트는 값이 아닌 형식을 검증한다.** CI는 UTC, 로컬은 KST로 동작하므로 값을
고정하면 한쪽에서 반드시 깨진다.

```js
// 나쁨 — CI(UTC)와 로컬(KST)에서 결과가 다르다
expect(TimeUtil.formatKoreanDate("2026-07-27T10:30:00Z")).toBe("2026년 7월 27일");

// 좋음 — 형식만 검증
expect(TimeUtil.formatKoreanDate("2026-07-27T10:30:00Z")).toMatch(/^\d{4}년 \d{1,2}월 \d{1,2}일$/);
```

값 자체를 검증해야 한다면 `jest.useFakeTimers()`로 시각을 고정하거나 타임존을 명시한다.

## 새 테스트를 쓸 때

1. **먼저 실패하는 테스트를 쓴다.** 통과부터 확인하면 그 테스트가 실제로 무언가를 검증하는지
   알 수 없다
2. 실행해서 **의도한 이유로 실패하는지** 확인한다
3. 구현한다
4. 통과를 확인한다

Phase 0에서 `src/utils/TimeUtil.test.js`를 만들 때 이 절차를 밟았다 — 통과를 확인한 뒤
일부러 기대값을 틀리게 바꿔 실패가 잡히는지 역검증했다. 인프라를 새로 세울 때는 이 역검증이
특히 중요하다. **테스트가 조용히 실행되지 않고 있어도 초록색으로 보이기 때문이다.**

## Phase별 테스트 계획

| Phase | 추가할 테스트                                                               |
| ----- | --------------------------------------------------------------------------- |
| 1     | 인증 유틸(토큰 저장·조회·삭제), axios 인터셉터(토큰 주입, 401 처리), 로거   |
| 2     | 라우팅 스모크, 진행도 가드, 점수 영속화                                     |
| 3     | 인증 모달 개폐·폼 검증, 랭킹 아이템 렌더                                    |
| 4     | 스토리 엔진 전이 규칙, **전 경로 회귀 테스트**(마이그레이션 전후 엔딩 동일) |
